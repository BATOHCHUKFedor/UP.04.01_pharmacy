# PocketBase: аптечный каталог

Зафиксированная версия: **0.40.5**. Здесь находятся миграции коллекций и JavaScript-обработчики
API, исполняемые самим PocketBase. Node.js нужен только для интеграционных тестов, не для сервера.

## Запуск на Windows

Распакуйте `pocketbase.exe` в этот каталог. После создания superuser достаточно:

```powershell
Set-Location -LiteralPath 'C:\Users\Asus F15\flutter_projects\pharmacy_project\backend\pocketbase'
.\pocketbase.exe serve
```

Перед запуском с новыми файлами остановите старый процесс через Ctrl+C. На Windows hooks
не обновляются автоматически. **Не удаляйте `pb_data`**: там SQLite, настройки и учётные записи.
До применения миграций к базе с важными записями сделайте резервную копию через панель PocketBase.

- Панель superuser: http://127.0.0.1:8090/_/.
- Проверка нашего API: http://127.0.0.1:8090/api/pharmacy/__health.
- Ответ проверки: `{"ok":true,"backend":"pocketbase","schemaVersion":1}`.
- Базовый адрес Flutter: `http://127.0.0.1:8090/api/pharmacy` — **не** просто `/api`.

Из корня Flutter-проекта, в другом терминале:

```powershell
flutter run -d chrome --web-port=5555 --dart-define=API_BASE_URL=http://127.0.0.1:8090/api/pharmacy
```

Адрес задаётся параметром, исходный код клиента не содержит адреса нового сервера.
После смены сервера нужен новый вход: старые токены мок-сервера PocketBase не принимает.
Публикация на GitHub Pages пока использует прежний API; переключение HTTPS выполняется отдельно.

## Первый администратор и фармацевт

Миграции **не** создают аккаунты с общедоступными паролями.

1. На экране регистрации Flutter создайте свою учётную запись. Публичная регистрация всегда
   назначает `customer`, даже если отправить другую роль вручную.
2. В панели PocketBase откройте коллекцию `pharmacy_users`, выберите созданную запись.
3. Измените только `role` на `admin`, сохраните. Не меняйте `code`, `usernameKey`, пароль и `active`.
4. В приложении выполните выход и повторный вход: профиль клиента загрузит актуальную роль.
5. Затем администратор может создавать пользователей и назначать роли через приложение.

Три значения ролей: `customer`, `pharmacist`, `admin`. Учётная запись `_superusers` — отдельный
административный доступ к PocketBase, её пароль и токен не передаются Flutter-приложению.
Старые аккаунты, бронирования и изменения `.mock-data/catalog.v1.json` автоматически не импортируются.
Старый файл сохранён; новый каталог создаётся из отдельного снимка учебных примеров `pb_hooks/seed.json`.

## Коллекции и связи

| Коллекция | Назначение и связи |
| --- | --- |
| manufacturers | Производители; один производитель — много препаратов |
| suppliers | Поставщики; множество производителей в relation-поле `manufacturers` |
| categories | Категории; множество категорий у препарата |
| drugs | Препараты; `manufacturer`, `supplier` — одиночные, `categories` — множественная связь |
| licenses | Лицензии; relation `supplier` и уникальный индекс обеспечивают одну лицензию на поставщика |
| pharmacy_users | Auth-коллекция пользователей приложения, хеширование паролей выполняет PocketBase |
| pharmacy_sessions | Сессии пользователя, сроки, отзыв и хеши refresh-токенов |
| pharmacy_reservations | Бронирования с реальными связями с пользователем и препаратом |
| pharmacy_config | Закрытые счётчики кодов и ключ подписи JWT |

Основных каталогов по-прежнему **пять**; технические коллекции не объявляются дополнительными
самостоятельными CRUD-разделами ради выполнения требования о восьми сущностях.

PocketBase хранит строковые идентификаторы записей. API возвращает числовой `code` как `id`,
чтобы сохранить совместимость Flutter-моделей. Внутри базы relation-поля ссылаются на настоящие
строковые PocketBase ID. Счётчики сохраняются транзакционно, удалённые коды не используются повторно.

## API и безопасность

Маршруты расположены под `/api/pharmacy`. Основные адреса остаются совместимыми:

| Адрес | Методы / назначение |
| --- | --- |
| /auth/register, /auth/login | POST: регистрация, вход |
| /auth/me | GET: текущий пользователь и сессия |
| /auth/refresh, /auth/logout, /auth/activity | POST: обновление, отзыв, отметка активности |
| /references | GET: справочники для форм |
| /drugs, /suppliers, /manufacturers, /categories, /licenses | GET: текущая страница; POST: создание |
| /{collection}/{code} | GET: карточка; PUT: изменение; DELETE: логическое удаление |
| /{collection}/{code}?hard=true | DELETE: физическое удаление, только администратор |
| /{collection}/{code}/restore | POST: восстановление, только администратор |
| /{collection}/bulk-delete | POST: атомарное логическое удаление массива `ids` |
| /drugs/{code}/dispense | POST: отпуск упаковок фармацевтом |
| /admin/users, /admin/users/{code} | GET/POST списка, PUT роли/доступности |
| /admin/statistics | GET: сводные показатели |
| /customers | GET/POST: работа фармацевта с пользователями |
| /reservations, /reservations/mine | GET: все бронирования для фармацевта / собственные для пользователя |
| /reservations | POST: оформление фармацевтом |
| /reservations/{code}/extend, /complete, /cancel | POST: продление пользователем / закрытие фармацевтом |

Параметры списков: `search`, `sort`, `page`, `size`, `includeDeleted`, `categoryId`,
`manufacturerId`, `supplierId`, `yearFrom`, `yearTo`, `country`, `usedOnly` — применяются
по смыслу конкретного раздела. Фильтрация, COUNT, ORDER BY, LIMIT и OFFSET выполняются в SQLite.
Имена полей сортировки проверяются по белому списку; значения SQL привязываются параметрами.
Для русскоязычного поиска используется нормализованный `searchText`, а не клиентская фильтрация.

Все стандартные record API-правила этих коллекций заблокированы (`null`). Обычные пользователи
не могут обойти серверные проверки через `/api/collections/.../records`. Доступ обеспечивает
только наш API после проверки Bearer JWT и живой сессии. Права каждый раз берутся из серверной
записи пользователя, не из роли в localStorage и не из поля `role` в JWT.

PocketBase выполняет хранение пользователей и хеширование паролей. Пару access/refresh и
ограничения сессии реализуют hooks: стандартный `authRefresh` PocketBase требует ещё действующий
токен и не заменяет предусмотренное проектом обновление уже истёкшего access-токена.
Refresh-токены хранятся только в виде SHA-256-хеша; после обновления старый токен нельзя использовать
для нового обновления. Выход отзывает сессию. Прошлый refresh разрешено использовать только
для отзыва при выходе во время незавершённого обновления.

Пароль приложения предварительно преобразуется в SHA-256 и затем хешируется штатным bcrypt
PocketBase. Это сохраняет прежний диапазон 8–128 символов, включая Unicode, без ограничения
bcrypt на 72 входных байта. Проверка при входе выполняет такое же преобразование. Пароли
пользователей приложения создавайте через его API, не напрямую в панели. Superuser использует
отдельный штатный механизм PocketBase, это преобразование к нему не применяется.

Ошибки предметной области: `401` — завершённая/недействительная сессия, `403` — нет прав,
`422` — `{message, errors: {field: message}}` для полей форм, `409` — конфликт остатков,
зависимостей или операции. Нативные ответы панели PocketBase остаются нативными и не входят
в контракт Flutter. Диагностика серверных внутренних ошибок не раскрывается клиенту.

Логическое удаление дочерних препаратов **не** снимает ссылочную защиту их справочников.
Физическое удаление препарата с историей бронирований запрещается, чтобы сохранить реальные связи.
Лицензия удаляется/восстанавливается вместе с поставщиком. Изменения выполняются транзакционно,
включая вложенную лицензию, групповое удаление и списание/возврат остатков.

Панель superuser предназначена для администрирования и может обходить бизнес-правила приложения.
Для повседневного CRUD используйте Flutter; не редактируйте вычисляемые ключи и relation-поля
напрямую в панели. Исключение при первом запуске — назначение роли первому администратору.

## Параметры сессии и учебные ошибки

В терминале сервера перед запуском:

```powershell
$env:PHARMACY_ACCESS_TTL = '60'
$env:PHARMACY_SESSION_TTL = '3600'
$env:PHARMACY_IDLE_TTL = '180'
$env:PHARMACY_DEBUG_API = '1'
.\pocketbase.exe serve
```

Значения по умолчанию: access — 900 секунд, общая сессия — 3600, неактивность — 180.
Предупреждение клиента — за 30 секунд. Новые общие сроки применяются при новом входе;
обновление токена и перезапуск страницы не продлевают общую сессию.

`PHARMACY_DEBUG_API=1` включает параметры `?__fail=500` и `?__delay=1500`.
Без этой переменной диагностические параметры игнорируются. Это ограничивает их использование
при размещении публичного API. Для остановленного сервера нажмите «Повторить» после его запуска.

Для ограничения CORS можно запускать:

```powershell
.\pocketbase.exe serve --origins='http://localhost:5555,https://batohchukfedor.github.io'
```

Источник должен совпадать с адресом клиентской вкладки; указываются схема, домен и порт,
без пути `/UP.04.01_pharmacy/`. CORS не заменяет авторизацию и проверку ролей.

## Проверки

Из корня проекта:

```powershell
node --test backend/pocketbase/test/integration.test.js
flutter analyze
flutter test
```

Интеграционные проверки запускают настоящий PocketBase на свободном порту с отдельным
временным `--dir`. Учётные записи случайные, рабочие `pb_data` и порт 8090 не затрагиваются.
Проверяются CRUD пяти каталогов, связи, пагинация/поиск/фильтры, ошибки 422/409, права,
откат транзакций, бронирования, вращение refresh, выход и сохранность после перезапуска.
Для Linux можно указать путь к бинарнику переменной `POCKETBASE_BIN`.

## Что ещё предстоит

- Ручная проверка текущего Flutter-клиента после переключения параметра API.
- Содержательная новая функция: оценка складских запасов и экспорт отчёта в CSV.
- Завершение проверки полей фильтров и критериев итогового задания.
- Совместный выбор HTTPS-размещения с постоянным `pb_data` и повторная публикация клиента.
  Render Free не предоставляет постоянный диск; прежнее размещение JSON-мока не решает
  сохранность SQLite. Для временной защиты возможен HTTPS-туннель к локальному PocketBase.

## Переход опубликованного клиента на Render PocketBase

Подготовлены `Dockerfile` и `.dockerignore`. Последний допускает в контекст сборки только
серверный код и миграции, не локальную базу, пароли и Windows-бинарник. Образ скачивает
Linux PocketBase 0.40.5. Локальная сборка Docker пока не проверена; первый deploy Render
должен подтвердить скачивание и запуск образа.

1. Зафиксируйте и отправьте серверные файлы, не добавляя `pb_data` и резервные копии:

   ```powershell
   git add .gitignore README.md backend/pocketbase
   git diff --cached --stat
   git commit -m "PocketBase: API and Render deployment"
   git push
   ```

   До commit проверьте, что среди ранее staged файлов также нет секретов или данных.
   Новый push может запустить существующие GitHub Actions и auto-deploy старого Render
   сервиса; на этом шаге они продолжают использовать прежнюю конфигурацию API.

2. В Render создайте **новый Web Service** из этого GitHub-репозитория. Старый Node.js
   сервис оставьте работающим до проверки перехода. Параметры нового сервиса:

   | Настройка | Значение |
   | --- | --- |
   | Name | pharmacy-pocketbase (либо другое свободное имя) |
   | Branch | main |
   | Language / Runtime | Docker |
   | Root Directory | backend/pocketbase |
   | Dockerfile Path | Dockerfile |
   | Docker Build Context Directory | . (относительно Root Directory, если поле присутствует) |
   | Docker Command | Не задавать: использовать CMD образа |
   | Health Check Path | /api/pharmacy/__health |

3. Тариф выбирайте осознанно:
   - **Free** — только демонстрация с возможным сбросом данных, аккаунтов и сессий
     при redeploy/restart/уходе в сон. Не объявляйте долговременную сохранность выполненной.
   - **Платный сервис + persistent disk** — для сохранности базы. Если этот вариант
     согласован, добавьте диск с Mount Path `/pb/pb_data` до первого запуска.
     Любая запись вне этого каталога по-прежнему временная.

4. При необходимости в Environment задайте `PHARMACY_ALLOWED_ORIGINS`:
   `https://batohchukfedor.github.io,http://localhost:5555`.
   Для демонстрации искусственных ошибок добавьте `PHARMACY_DEBUG_API=1`;
   без неё `__fail` и `__delay` игнорируются. `PORT` вручную не требуется:
   Docker CMD использует значение Render. Локальные TTL-переменные PowerShell в облако
   не переносятся, defaults — access 900, session 3600, idle 180 секунд.

5. Запустите deploy, дождитесь Live и скопируйте **фактический** HTTPS-адрес из панели.
   Откройте `{SERVICE_URL}/api/pharmacy/__health` — ожидается `backend: pocketbase`.
   Если скачивание бинарника или запуск завершились ошибкой, сначала исправьте deploy,
   не переключая клиент. Не предполагайте, что адрес нового сервиса совпадает со старым.

6. Облачная база отдельная: локальные пользователи автоматически не переносятся.
   Создайте superuser через первоначальную установку PocketBase. Ссылка установки
   находится в Logs нового сервиса; замените её хост/порт на фактический HTTPS-адрес,
   сохранив путь и fragment. Установочный токен и пароль не присылайте в чат и не
   публикуйте в отчёте. Если нужна копия локальной базы вместо нового каталога,
   сначала согласуйте перенос через приватную резервную копию, не Git.

7. В GitHub: Settings → Secrets and variables → Actions → Variables измените
   **repository variable** `API_BASE_URL` на `{SERVICE_URL}/api/pharmacy`.
   Не указывайте адрес панели `/_/` и не добавляйте токен. Затем Actions →
   Flutter Web — GitHub Pages → Run workflow → main. Одно изменение переменной
   не вызывает новую сборку автоматически.

8. После успешного workflow откройте опубликованный клиент, обновите с обходом кеша
   и выполните новый вход. При пустой облачной базе сначала зарегистрируйте аккаунт,
   назначьте `admin` в облачной `pharmacy_users` через superuser и войдите повторно.
   Локальные назначения ролей не являются назначениями в облаке.

9. Проверьте Network: запросы уходят на новый HTTPS-хост и `/api/pharmacy/...`.
   Создайте категорию, проверьте её в **облачной** панели. На сервисе с диском
   перезапустите сервис и подтвердите, что запись и аккаунт остались. Проверьте прямую
   ссылку на внутренний экран и обновление страницы. Старый API отключайте только
   после успешной проверки и отдельного решения; удалять сервис не обязательно.

Для итогового отчёта фиксируются фактический API-адрес, runtime Docker, путь постоянного
диска (либо честное ограничение Free), CORS-origin, health-check, параметр сборки и проверка
новой публикации. Не выдавайте старые снимки Node.js API за подтверждение работы PocketBase.
